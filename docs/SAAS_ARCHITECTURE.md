# SaaS architecture

## Request boundary

Origin -> /s/{slug} -> TenantContext -> registry record -> customer database -> Router -> controller -> models -> ContentRepository -> template.

Platform /signup and /login do not instantiate content models. Unknown site slugs return 404. Database names are generated by the server and stored in the registry; request values never become SQL database identifiers. Signup marks a site active only after initialization. Failed provisioning removes only the database and registry record allocated by that call.

The existing portfolio remains portfolio_db under the demo slug. Every new customer receives a randomly named portfolio_site_* database, including admin_users, messages, projects and settings. The registry stores website identity and owner email; the password hash belongs to the customer's admin_users table.

## Authentication and media

Session cookies are named by site ID, scoped to its URL path, HttpOnly and SameSite=Lax. Login regenerates the session ID and records the site ID. Authentication checks the site ID even if a caller copies a cookie to another site's cookie name. Content-controller POSTs check CSRF tokens; forms receive hidden tokens and same-origin fetch mutations send the token header.

Uploads are verified using their bytes, receive random filenames and server-chosen extensions, and are stored under assets/uploads/sites/{siteId}/. Allowed types: JPG, PNG, GIF, WebP and PDF. Uploaded SVG/HTML/script content is rejected. Published files are public; the media catalog and deletion use the site's database. Deletion also checks the current site's storage prefix.

Legacy login-bypass/debug PHP scripts return 404. The development router and Apache rules do not execute other public PHP entry points.

## Editing contract

Hero, projects, services, skills, timeline, testimonials and page records retain their specialist editors. WebsiteContent handles previously hard-coded text and section controls. The checked-in field catalog is allowlisted on save and grouped by page. Text is escaped on output. Visibility is server-rendered; ordering rearranges top-level section blocks.

settings_site is canonical for identity, contact data, logo/favicon, navigation CTA, footer text and social/footer links. The legacy Setting model remains for theme and supplemental settings, mapping shared identity keys into settings_site. The website editor selects uploaded media IDs from the current customer's media table.

Browser metadata is separate from visible headings. Public rendering enforces page publication status. The generic page form links to the actual content editor rather than exposing a body field unused by most templates.

## Validation and boundaries

HTTP tests use two customer accounts and verify editing propagation, cross-customer session rejection, missing-CSRF rejection, spoofed-upload rejection, image URLs, visibility/order, theme/footer settings, 22 dashboard screens and inline JavaScript syntax. Visual browser interaction remains unverified.

The runtime database credential is shared. Database-per-customer does not mean separate server/process isolation. Production needs constrained credentials, provisioning jobs, abuse controls, quotas, account recovery, monitoring and backups. Billing and custom domains are not implemented.
